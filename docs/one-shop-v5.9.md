# 원샵 5.9 · 여러 기기에서 함께 처리하는 직원 주문함

## 사용 흐름

1. 사장님앱에 데모 로그인하고 **직원과 권한 → 실시간 샵 연결**을 누른다. 이 브라우저에서 이전에 연결한 샵이 있으면 재사용한다. 로컬 직원 이름·역할·권한을 같은 샵의 서버 직원 목록에 연결한다. 로컬 샘플 주문은 올리지 않는다.
2. 연결된 화면에서 직원을 등록하고 개인별 직원 링크를 전달한다. 화면의 **이 샵 손님앱 열기**로 같은 샵의 QR/손님 주문을 시험한다. 이미 클라우드 샵을 관리 중이면 바로 직원 등록 화면을 사용한다.
3. 직원은 자기 휴대폰에서 링크를 열면 그 샵의 실제 데모 주문 목록을 받는다. 홀은 접수·서빙, 주방은 준비 시작·준비 완료를 처리한다. 사장님과 손님도 기존 Broadcast 갱신 경로를 통해 같은 상태를 확인한다.
4. 사장님이 권한을 수정하거나 직원을 삭제하면 기존 직원 기기에도 반영한다. 링크 재발급은 모든 이전 링크를 무효화한다. 직원 처리 이력에는 담당자·대상·시각을 남긴다.

## 구현

- `modu_staff`: 샵 소속, 역할, 정규화된 권한, 토큰 해시, 권한 버전, 만료·삭제 시각.
- `modu_staff_audit`: 등록·권한 변경·재발급·삭제·직원 업무 처리 기록. 조회는 사장님 전용.
- API `GET/POST /:store/team`, `PATCH /:store/team/:member`: 소유자 전용 목록·등록·권한/링크 관리.
- API `GET/PATCH /:store/staff/:member`: 직원 전용 최소 데이터 조회와 허용된 업무 처리.
- DB RPC는 서비스 역할에서만 실행한다. 앱의 테이블과 함수에 대한 anon/authenticated 직접 접근은 차단하고 RLS를 유지한다.
- 직원 등록 상태·현재 권한을 검사하는 트랜잭션 안에서 직원 행을 잠그고 업무를 처리한다. 동시에 삭제·권한 수정이 도착해도 이미 시작한 트랜잭션과 순서가 정해진다. 삭제가 완료된 뒤 들어온 요청은 거절한다. UI에서 버튼을 숨기는 것만으로 접근을 제어하지 않는다.
- 직원 응답에는 사장님 운영 메모·대화 전체·직원 목록·토큰 해시가 없다. 배달 주소·전화는 `deliveryView`, 금액은 `salesView`를 허용해야 응답에 포함한다. 메뉴 변경은 판매 가능 여부, 샵 설정 변경은 연락처만 가능하다.
- 기존 `modu:<shop>` 채널에는 빈 갱신 신호만 보낸다. 주문·직원 변경마다 각 기기가 자기 권한으로 API를 다시 조회한다. 20초 보조 동기화와 온라인 복귀 재조회가 있다. 직원 화면은 연결 끊김·탭 숨김 때 데이터를 숨기며, 돌아오면 권한을 재확인한다. 갱신 전에 시작된 오래된 응답은 버린다.

## 초대 링크와 현재 경계

직원 링크는 256비트 난수 접근 키를 URL fragment로 전달한다. 서버에는 SHA-256 해시만 저장한다. fragment는 초기 진입 즉시 주소에서 지우고, 이후 해당 기기의 로컬 저장소에서 읽어 요청 헤더로 보낸다. 직원 화면에는 `no-referrer`를 적용했다. 링크는 30일 후 만료된다. 원본 링크는 발급한 사장님 기기에서만 다시 복사할 수 있고, 다른 기기는 재발급해야 한다. 이전 링크의 보관 복사본을 재사용해도 서버가 거절한다.

이 링크는 직원 본인 확인이 아니라 **소지자에게 해당 직원 권한을 부여하는 데모 접근 방식**이다. 지정된 직원에게만 전달해야 한다. 실제 이메일·Google 계정 인증은 연결하지 않았으며, 사장님도 기존 관리 브라우저를 유지해야 한다. 모든 기기의 계정 복구를 구현한 것으로 표시하지 않는다.

기존 `?role=floor` / `?role=kitchen` 링크는 계속 독립적인 로컬 역할 미리보기다. 새 직원 실시간 링크는 `?store=...&member=...#access=...`로 발급한다. 샵이 있는 직원 경로는 로컬 역할 화면으로 대체하지 않는다. 실제 AI·결제는 추가하지 않았고 서버 주문의 결제 상태는 계속 `unpaid` 제약을 따른다.

## 검증

- 자동 검사 60개: 기존 주문·예약·언어·권한 검사와 함께 오래된 응답 무시, 오프라인 데이터 숨김/실행 차단, mutation 중 재조회, 초대 키 제거·범위 제한, 서버 입력 검증, 9개 언어 문구.
- 실서버 직원 API 48개 응답 검사: 별도 접속 조회, 홀/주방 처리 → 사장님/손님 상태 일치, 타 샵 차단, 주소·금액 최소 공개, 권한 버전 충돌, 재발급/삭제 후 이전 키 거절, REST/RPC 직접 접근 차단. 변경 Broadcast에 비공개 데이터가 없는 것도 확인.
- 기존 클라우드 저장·주문 중복 방지·예약·사진·격리 회귀 검사 통과.
- Supabase 보안 advisor에서 새 경고 없음. 두 새 테이블의 RLS와 클라이언트 접근 거부를 쿼리로 확인.
- 로컬 브라우저의 서로 다른 origin에서 사장님, 베트남어 손님, 홀, 주방 연결. 손님 7번 테이블 주문 → 홀 접수 → 주방 준비 시작/완료 → 사장님 주문함과 손님 라미 알림의 같은 상태를 확인.

Supabase 구현 참고: [Broadcast](https://supabase.com/docs/guides/realtime/getting_started), [Realtime 권한 갱신](https://supabase.com/docs/guides/realtime/authorization#updating-rls-policies). 채널 권한 갱신에만 의존하지 않고 업무 API에서 매번 현재 직원 권한을 검사한다.
